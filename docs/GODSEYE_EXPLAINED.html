Godseye: architecture, models and storage, explained from the code

Godseye watches many CCTV cameras, writes down who and what it saw (where, when, which camera, with video proof), and lets you ask questions in plain English such as “show me the man in the red jacket on the gate camera this morning”. Every answer is built only from stored records.

How this page was made: every statement was checked against the source code at commit 83de6a4 (2026-10-08). The example rows and file names in the storage section come from a real run of the project's own storage code (EvidenceStore with SQLite, ChromaDB 1.5.9 and ffmpeg) fed with a made-up scene: two cameras, one person and one car. The values are real outputs of the code; the scene is synthetic.

Four rules that hold everywhere

  1. track_id and global_id are different things. track_id is a small number given by ByteTrack on one camera (“person #3 on the lobby camera”). global_id (e.g. person-92a28feeb303) is given by FastReID matching and means “the same individual across cameras”. They are stored in separate columns and never reused for each other.
  2. The LLM's output is data, never a command. It produces JSON that is validated field by field. It cannot run SQL, shell commands or file operations, and there is a test that scans the query code for such calls.
  3. Track A and Track B only share the disk. No function calls, no shared memory. Track B opens godseye.db with mode=ro and PRAGMA query_only=ON.
  4. Answers are grounded. Every camera, time, id and clip in an answer comes from a stored row. If nothing is stored, the answer says so and adds that this does not prove absence.

1 Capture & prepare

Goal: turn live camera streams into a steady, small number of clean frames per second, each labelled with its camera and capture time.

Ingest & decode (GStreamer)

GStreamer is a media framework: you chain “elements” into a pipeline. Each camera gets its own pipeline and thread:

rtspsrc  ! decodebin ! videoconvert ! video/x-raw,format=BGR ! appsink max-buffers=2 drop=true
(rtmp2src | souphttpsrc+decodebin3 for HLS | filesrc for replay)
  • Source receives the network stream, decodebin picks the right decoder (H.264 via libav), videoconvert converts to BGR pixels, appsink hands frames to Python.
  • max-buffers=2 drop=true: if Python is slow, old frames are dropped instead of building up delay.
  • Reconnect with back-off, a watchdog for stalled streams, and a counter called stream_epoch that goes up by one on every reconnect. Trackers reset when it changes, which is why tracks are keyed by (camera_id, stream_epoch, track_id) later.
  • Camera passwords are written as ${ENV_VAR} in the config and are redacted from error messages.

Frame sampler

Running AI on every frame of a 25 fps camera is wasteful. The sampler (godseye/ingest/sampler.py) decides which frames go on:

RuleDefaultWhy
Base rate2 frames per secondenough to follow walking people
Burst rate on motion5 frames per secondMOG2 background subtraction says ≥ 0.5% of pixels changed
Redundancy dropmean grey-level difference < 1.0 on a 160-px thumbnaila static scene does not need re-analysing
Keepaliveat least one frame every 5 sproves the camera is alive even when nothing moves

Preprocess

  • Privacy masks: rectangles that are blurred (Gaussian) or blacked out, for example a neighbour's window. If masks are configured, the storage layer refuses to save an unmasked original.
  • Letterbox to 640×640 (keep aspect ratio, pad with grey value 114), convert BGR → RGB, scale pixels to float32 values between 0 and 1.
  • Keeps a full-resolution copy original_bgr (uint8) for the detector, Re-ID crops and evidence clips.

2 See (AI perception)

One worker thread (PerceptionPipeline.process, godseye/perception/pipeline.py) runs four steps on each sampled frame. The GPU models are shared by all cameras.

Detect · NanoOWL (OWL-ViT)

You give the detector text prompts and it finds matching objects. The prompts in config/perception.yaml:

Prompt textStored labelRe-ID classThreshold

What is and is not stored. Only objects matching these prompts exist anywhere in the system. All 6 labels are stored (tracks, observations, track_clip vectors, clips), but only person and vehicle (car, truck, bus) get a cross-camera global_id, because FastReID models exist only for those two (the identities table even has CHECK (reid_class IN ('person','vehicle'))). Motorcycles and bicycles are stored as other with no identity. Handbags, suitcases, backpacks and any other object are not prompted, so they are not detected or stored at all. The storage schema itself is not the blocker: tracks.label is free text and other exists. The blockers are (1) the prompt list, (2) Track B's 6-label vocabulary, (3) no link between a person and the bag they carry, and (4) no Re-ID model for bags. The only approximation today is asking about a person with a description (e.g. “person with a red handbag”): the CLIP ranking of person tracks may reflect the bag, but that is unvalidated and still returns people, not bags.

After scoring: boxes smaller than 8 px are dropped, overlapping boxes of the same label are merged by NMS (IoU 0.5), at most 100 detections per frame, boxes are converted to original-frame pixels. Measured: about 10 ms per frame on the RTX 5050 with TensorRT FP16.

Embed · reused vector (no extra model)

Inside OWL-ViT, every image patch produces a 512-number “class embedding” that is compared with the prompt's text embedding to score it. Godseye keeps that vector for each detection instead of running a second CLIP model. It is normalised to length 1 and checked (shape 512, finite, norm 1 ± 0.001). Per track, the vectors are averaged and normalised again; this average is what gets stored in ChromaDB track_clip and is what makes “red jacket” search possible.

Track · ByteTrack

  • One ByteTrack instance per class group (person / vehicle / other) per camera, so a person box can never be joined to a car track.
  • Gives each object a track_id 1, 2, 3… that is unique only on that camera and that stream_epoch.
  • Keeps per track: hits (frames matched), first/last seen, the most-voted label, a trajectory of the last 50 centre points, and the mean reused embedding.
  • A track ends as lost_timeout after about 5 sampled frames without a match (1–2.5 s at 5–2 fps), stream_restart on reconnect, or shutdown.

Re-identify · FastReID + identity resolver

FastReID turns a cropped person or vehicle into 2048 numbers that describe appearance. Two crops of the same person give similar vectors, even on different cameras. The resolver (godseye/perception/identity.py) then decides the global_id:

  1. Crops are skipped if more than 30% covered by another box (occlusion), shorter than 48 px, or with an implausible shape (person height/width outside 0.8–4.0).
  2. After 3 good crops, their average vector is compared to the gallery (all known identities, stored in ChromaDB).
  3. Decision rules:
Best similarityResultWhat gets stored
≥ 0.70 and beats the second-best identity by ≥ 0.05matchedexisting global_id; the vector is added to that identity's exemplars
below 0.55 (or empty gallery)newnew global_id like person-92a28feeb303
in between, or too close to the runner-upambiguousno global_id; top-3 candidates and scores saved; one re-check at 8 crops; never force-merged

An identity currently visible on the same camera under a different track is excluded (one person cannot be two tracks on one camera at once). Motorcycles and bicycles get not_applicable. The design is deliberately conservative: a missed merge creates a duplicate identity (fixable), a wrong merge would mix two people's paths (dangerous).

Honest caveat: the thresholds 0.70 / 0.05 / 0.55 are defaults, not calibrated on real site footage. On Market-1501 (a public dataset from a different domain) Rank-1 was 0.62. In a 40-person test there were 0 wrong merges, 15 correct matches, 10 ambiguous and 15 new. Vehicle Re-ID is not validated.

CLIP, the idea underneath

CLIP (OpenAI, 2021) was trained on hundreds of millions of image–caption pairs so that an image and a sentence describing it end up as nearby vectors in the same 512-number space. That is why you can compare a picture with words: you compare their vectors.

OWL-ViT and NanoOWL

OWL-ViT (Google, 2022) starts from CLIP and turns it into a detector. A Vision Transformer cuts the 768×768 image into 32×32-pixel patches (24×24 = 576 patches). For every patch, a small head predicts a box and another head predicts a class embedding. The embedding is compared with the text prompts' embeddings; a high score means “this patch contains a person”. Because the classes are just text, you can detect new things by changing a prompt, with no retraining.

NanoOWL is NVIDIA's project that makes OWL-ViT fast by compiling the image encoder with TensorRT. Godseye uses NanoOWL's own predictor unchanged (pinned commit fb553dee) and adds a TensorRT 11 engine loader, a decoder that remembers which patch each box came from (so the embedding can be reused), NMS and provenance.

TensorRT, FP16

TensorRT is NVIDIA's inference optimiser: it fuses layers and picks the fastest GPU kernels for this exact GPU. The engine is built once (about a minute), cached in models/nanoowl/, and its SHA-256 is recorded as provenance. FP16 means 16-bit floats for the maths: about twice as fast as 32-bit with negligible accuracy loss for detection.

ByteTrack

ByteTrack (2022) links boxes across frames. A Kalman filter predicts where each track's box should be next from its past motion. The Hungarian algorithm then finds the best one-to-one pairing between predicted boxes and new detections using box overlap (IoU). ByteTrack's twist: it first matches high-confidence detections, then tries the low-confidence ones against the leftover tracks. Low scores often mean a partly hidden person, so this keeps tracks alive through occlusion.

FastReID SBS R50-ibn

FastReID is an open-source re-identification toolbox. The model is a ResNet-50 network with IBN (Instance-Batch Normalization) layers; IBN makes features less sensitive to colour and lighting differences between cameras. “SBS” is FastReID's stronger-baseline training recipe. It was trained so that crops of the same person are close and crops of different people are far apart. Output: 2048 numbers, normalised to length 1. Weights: MSMT17 (a large multi-camera person dataset) and VeRi-776 (vehicles). The loader fixes a key-naming difference in the released checkpoints and refuses to run if any weight is missing.

Qwen3-8B on Ollama

Qwen3-8B is an open-weight 8-billion-parameter language model from Alibaba's Qwen team. Ollama runs it locally (loopback address only; a non-local URL is rejected). Settings: temperature 0 (deterministic), context 4096 tokens, thinking mode off, and a JSON schema passed as format so the model can only produce JSON of that shape. Pydantic then re-validates it strictly. Measured: about 6 GB of VRAM when loaded, 1.2 s median per question locally. It can be moved to a second PC's GPU through a Ray gateway.

5.3 Why not use a single database?

Because the data comes in three completely different shapes, and each shape needs a different kind of engine to be searched fast.

Facts with exact filters → SQLite

“camera = lobby_cam AND time between 9 and 10 AND label = person”. Relational databases are built for exact filters, joins between tables, counts, transactions and indexes. SQLite is a single file with no server, which fits a single local machine. It is required by the project specification.

“Find the most similar” → ChromaDB

“Which of 10,000 stored 2048-number vectors is closest to this one?” SQL cannot do that efficiently: it would read every row and do 2048 multiplications each. ChromaDB keeps an HNSW index, a graph that jumps to the nearest neighbours in a handful of steps. Also required by the specification.

Large binary video → files

A clip is megabytes. Video players, browsers and ffmpeg understand MP4 files directly and can seek inside them; putting blobs in a database bloats it and makes backups and deletion painful. The database stores only the path, size, SHA-256 and frame times.

Why is knowledge.db separate from godseye.db? Because Track B must never write into Track A's evidence database. That keeps the evidence tamper-proof from the chat side (it is opened read-only), keeps the single-writer rule simple (Track A holds a lock), and lets you wipe the learned names without touching evidence.

What is the cost of splitting? No transaction can cover SQLite, ChromaDB and files at once. Godseye handles that with a strict write order, a recovery step on start-up and a reconcile tool (see 5.15). Say this openly; it shows you understand the trade-off.

Good to know: ChromaDB itself keeps an internal SQLite file (chroma.sqlite3) for ids, metadata and its write log. The similarity search, however, is done by the HNSW index files next to it. So “Chroma is just SQLite” is not true, and Godseye's own facts are not stored there.
We split by data shape: exact facts in SQLite, similarity search in ChromaDB, video as files. SQLite is the source of truth; the other two are linked to it by ids. Since no transaction can span all three, we write in an order that can only ever leave harmless orphans, never a reference to something missing, and we have recovery and reconcile tools for those orphans.

5.4 Primer: the concepts you must be able to explain

Vector / embedding

A vector is just a fixed-length list of numbers. An embedding is a vector produced by a neural network so that similar things get similar numbers. Godseye stores two kinds:

VectorLengthProduced byMeansStored in
Re-ID feature2048FastReID“what this individual looks like” (clothes, build, colours), tuned to tell individuals apartChroma reid_person / reid_vehicle
CLIP-space track vector512OWL-ViT (reused), averaged per track“what this object looks like in words space”, comparable with text like “red jacket”Chroma track_clip
Text query vector512OWL-ViT text towerthe meaning of the words typed by the usernot stored (computed per question, cached in RAM)

Only vectors from the same model can be compared. A 2048-d Re-ID vector and a 512-d CLIP vector live in different spaces.

float32

Each number in a vector is a 32-bit floating-point number (IEEE-754 single precision): 4 bytes, about 7 significant decimal digits. So a 2048-d Re-ID vector is 2048 × 4 = 8,192 bytes and a 512-d CLIP vector is 2,048 bytes. This was verified on the demo store: each HNSW slot of reid_person is 8,332 bytes = 8,192 (vector) + 132 (graph links) + 8 (label). Why float32 and not float64? Half the memory and disk, GPU-native, and similarity does not need more precision. (In SQLite, by contrast, every REAL is an 8-byte float64, used for timestamps and box coordinates.) In code the arrays are numpy.float32; FastReID computes in FP16 on the GPU and converts the result to float32.

Normalisation (length 1)

Every vector is divided by its own length so that its length becomes exactly 1 (“L2-normalised”). Then only the direction matters, not the size, and the dot product of two vectors equals their cosine similarity.

Cosine similarity and “cosine space”

Cosine similarity measures the angle between two vectors: cos = (a·b) / (|a| |b|). It goes from 1 (same direction, “the same”) through 0 (unrelated) to −1 (opposite). Chroma reports a distance instead: distance = 1 − cosine, so 0 means identical. Godseye converts back: similarity = 1 − distance (vectors.py, retrieval.py).

“Cosine space” is the collection setting {"hnsw:space": "cosine"} given when each collection is created. It tells Chroma which distance to build its HNSW index with (others are l2 and inner product). All three Godseye collections use cosine (verified in the demo: metadata={'hnsw:space': 'cosine'}).

Try it: cosine calculator

Try -0.6, -0.8 (opposite, cosine −1) or 0.8, -0.6 (unrelated, cosine 0). Real vectors have 512 or 2048 numbers, but the maths is identical.

HNSW (how Chroma finds nearest vectors fast)

Hierarchical Navigable Small World is a graph index. Every vector is a node linked to its closest neighbours (Chroma's default M = 16, so up to 32 links per node on the bottom layer; the 132-byte link block in each file slot matches exactly that). Upper layers contain few nodes with long links, like motorway exits; the bottom layer contains every node. A search starts at the top, greedily walks towards the query, drops a layer, and repeats. It is approximate nearest neighbour (ANN) search: extremely fast and almost always exact at Godseye's scale. Godseye asks for the top 100 exemplars (chroma_query_k) and then picks the best exemplar per identity.

SHA-256

A cryptographic hash function: it reads a file of any size and outputs a 256-bit fingerprint, written as 64 hexadecimal characters. The same input always gives the same fingerprint; changing a single byte gives a completely different one; finding two different files with the same fingerprint is practically impossible.

Other terms used below

  • Epoch timestamp: seconds since 1970-01-01 00:00 UTC, as a decimal number. 1791450900.0 = 2026-10-08 09:15:00 UTC. Easy to compare and subtract; converted to readable time only in the answer text.
  • Primary key (PK): the column that uniquely identifies a row. Foreign key (FK): a column that must contain a value that exists in another table's key; SQLite enforces this here (PRAGMA foreign_keys=ON).
  • UNIQUE constraint: forbids two rows with the same combination of values. Used to make writes idempotent.
  • Upsert: “insert, or update if it already exists” (INSERT … ON CONFLICT … DO UPDATE in SQLite, upsert in Chroma).
  • Idempotent: doing it twice has the same effect as once.
  • Transaction: a group of writes that either all happen or none (BEGIN IMMEDIATE … COMMIT/ROLLBACK).
  • Index: a sorted lookup structure that lets the database jump to matching rows instead of scanning the whole table.
  • WAL (write-ahead logging): SQLite mode in which a writer and many readers can work at the same time. That is what lets Track B read while Track A writes.
  • JSON in a TEXT column: small lists stored as text, e.g. frame_ts and identity_candidates.

5.9 Clip store: the video evidence

  • Layout: clips/{UTC date}/{camera_id}/{start time in ms}_{8 random hex}.mp4. The date and camera folders keep directories small and make retention easy.
  • When recording happens: only while a camera has at least one track. One segment per camera (shared by all its tracks), not one per track. A segment closes after 5 s with no tracks (idle_close_s), after 60 s maximum (max_segment_s), or on a reconnect / resolution change. No pre-roll.
  • Encoding: raw BGR frames are piped to ffmpeg → libx264 H.264, CRF 26, preset veryfast, yuv420p, +faststart (playable while streaming), playback 5 fps, 2 encoder threads and no lookahead (measured: the defaults used ~240 MB RAM per camera and pushed 8 cameras into swap).
  • Playback speed: frames are captured at 2–5 fps but play at 5 fps, so a clip can play faster than real life. The demo lobby clip covers 5.5 s of real time in 12 frames (2.4 s of video). clips.frame_ts gives each frame's real time.
  • Disk guard: no new clip is started with less than 2 GiB free (min_free_bytes).

Publish protocol (why a clip in the database is always a real, playable file)

  1. Frames are written to <name>.mp4.part, never directly to the final name.
  2. On close: ffmpeg must exit with code 0.
  3. ffprobe must confirm: codec is H.264, size matches, packet count equals the number of frames written.
  4. SHA-256 and size are computed, the file is fsynced to disk.
  5. Atomic rename .part → .mp4, then the folder is fsynced.
  6. Only now the clips row is inserted and the waiting observations get their clip_id, in one transaction.

If anything fails (ffmpeg missing or killed, low disk, validation): the .part is deleted, the observations keep clip_id = NULL, an ERROR is logged, health() counts it, and that camera's clips pause for 30 s. Metadata keeps flowing; only video is lost for that window. This is “degrade, don't crash”.

5.12 When things are written

Track A's service loop (godseye/runtime/service.py) takes one frame, runs perception, then calls EvidenceStore.write(enriched_frame). Inside one call (godseye/storage/store.py), in this order:

  1. Safety checks. Camera id must be path-safe; if privacy masks are configured, the original must be masked, otherwise the frame is refused.
  2. Vectors first (ChromaDB). Upsert track_clip for tracks whose hits are a multiple of 10 and for tracks ending now. Idempotent.
  3. Media second (clip). If the camera has tracks, open a segment if needed and pipe this frame to ffmpeg; the frame's index becomes clip_frame. Clip problems degrade, never raise.
  4. Metadata last (one SQLite transaction). Upsert cameras; for each live track: upsert identities (if it has a global_id), upsert tracks, insert one observations row (INSERT OR IGNORE, so duplicates are skipped); for each ended track: set end_ts, end_reason, final global_id and embedding_id. Commit, or roll back everything on error.
  5. Later, when the segment closes: validate and publish the clip, then one transaction inserts the clips row and fills clip_id on the waiting observations.

Separately, during the Re-ID step (inside perception, before write), PersistentGallery writes Re-ID exemplars to reid_person/vehicle and then the identities row. Same principle: the vector first, the row that refers to it second.

The rule behind the order: always write the thing that is pointed to before the thing that points to it. A crash in between can then only leave an orphan (a vector or file nobody points to, harmless and cleaned by reconcile), never a dangling reference (a row pointing to a missing vector or video, which would be a broken answer). Deleting goes the other way round: purge_clips removes the database reference first, then the file.

5.14 How the stores help each other

  1. SQLite narrows, Chroma ranks. SQL cuts thousands of tracks down to “persons on lobby_cam this morning”; Chroma then orders only those by similarity to “red jacket”. Neither could do the job well alone.
  2. Chroma decides identity, SQLite records it. The Re-ID gallery in Chroma says “this is person-92a2…”; SQLite stores that on the track; path questions then just group tracks by global_id.
  3. SQLite points into the video. clip_id + clip_frame + frame_ts turn a database row into the exact second of video, and the boxes from observations are drawn on it.
  4. knowledge.db translates human words into database keys (camera ids, global_ids, zones), which then become SQL filters.
  5. SQLite guards the others. Reconcile compares SQLite with Chroma and the files to find orphans and missing or altered clips.

5.16 Growth, retention and privacy (be honest)

  • Growth: one observations row per tracked object per sampled frame. Example arithmetic (not a measurement): 10 people continuously visible at 5 fps = 50 rows per second on that camera. Vectors: up to 20 × 8 KB per identity, 2 KB per track. The real growth rate over days has not been measured.
  • Retention: only clips can be purged (purge_clips(before_ts), manual): files and clip rows go, track metadata stays with NULL clip references. No automatic schedule, no expiry of identities.
  • Privacy: masks are enforced before storage. Not yet done: encryption at rest, deleting one person's data (the Re-ID vectors are biometric-like data).

Step 2 · Code does the time maths

The LLM only extracts “yesterday, 15:00–17:00”. timeres.py turns that into epoch seconds. This was a deliberate decision: during testing, the model answered “yesterday” with the wrong year. Times in the future are rejected with a clarification.

Step 3 · Referent resolver: words → real ids

Each mention (object, camera, identity) goes through a cascade, never jumping straight to the LLM. Every stage can only return one of the real candidates.

  1. Exact: normalised text equals a camera id / label, or a configured synonym.
  2. Learned: an alias in knowledge.db.
  3. Fuzzy: string similarity ≥ 0.85 and clearly ahead of the runner-up (typos like “lobyy”).
  4. Semantic (objects only): OWL-ViT text vectors, cosine ≥ 0.55 with a 0.10 margin (“guy” → person, “SUV” → car).
  5. LLM choice: the model picks an index from the offered list, or null. An index outside the list is discarded.

Pronouns (“he”, “that car”) are resolved only from the conversation: the last identities shown in this session. One candidate → used; several → the user chooses; none → the user clicks on the person in a camera view.

5 Find & answer

Query planner (deterministic)

make_plan maps intent → one of five allow-listed operations: find_tracks, count_tracks, locate_latest, when_seen, path. The QueryPlan holds camera, time, spatial, object and identity filters, an optional semantic text (attributes + label), a ranking (recency / confidence / duration / semantic) and a limit (default 10, max 50). validate_plan rejects it before any retrieval if a camera or identity does not exist, the time range is backwards, the label is unknown, the limit is too high or there is no subject. A rejected plan gives SYSTEM_ERROR, never a guessed answer.

Retrieve

SQL filter → optional spatial filter → optional Chroma similarity ranking → best evidence clip per result. Up to 2000 candidates; if that cap is hit the answer is marked partial and suggests narrowing.

Reconstruct path

For one global_id: tracks sorted by time; tracks on the same camera less than 30 s apart are merged into a visit (OBSERVED). Between two visits is a transition, always marked INFERRED (nobody saw the person walk between cameras), with a verdict:

VerdictMeaning
plausiblegap ≥ fastest possible route in the configured camera topology
unverifiedno topology configured (the default today): the answer says so
impossible_too_fastfaster than physically possible → warns that the global_id may cover two different people
impossible_overlapseen on two non-overlapping cameras at the same time
impossible_no_routeno route between the cameras
long_gapmore than 600 s apart: a new episode, no link claimed

Build response

Text comes from templates filled with retrieved values (camera, time, duration, identity and status, mean confidence, similarity, clip path and frame). Statuses: OK, NO_RESULT (with “this does not prove absence”), PARTIAL_EVIDENCE (missing clip, confidence below 0.35, unverified transitions, capped results, unidentified tracks in a count), AMBIGUOUS_RESULT (several individuals, choose one), SYSTEM_ERROR. Optional LLM rewording (off by default) is accepted only if every number, id and camera survives, nothing new is added, and OBSERVED/INFERRED labels are unchanged. Afterwards the identities shown are remembered in the session for follow-up pronouns.

9 · Questions a jury is likely to ask

Why three (four) stores instead of one database?
Different data shapes. Exact facts and relations → SQLite. Nearest-vector search → ChromaDB's HNSW index (SQL would have to scan every vector). Megabyte video → files that players can stream and seek. Track B's learned names go into a separate SQLite file so the chat side can never write to the evidence. The trade-off is no cross-store transaction, which we handle with write ordering, recovery and reconcile.
What exactly is a vector here, and what does cosine similarity mean?
A vector is a list of numbers produced by a neural network: 2048 numbers from FastReID describing a person's appearance, or 512 from OWL-ViT in CLIP space. All are normalised to length 1. Cosine similarity measures the angle between two vectors: 1 = same direction (very similar), 0 = unrelated. Chroma stores them in “cosine space” and returns distance = 1 − similarity.
Can it find a “red handbag” or a “large suitcase”?
Not today. The detector is open-vocabulary, but it is configured with prompts for people, cars, trucks, buses, motorcycles and bicycles only, and the question side accepts only those six labels. Adding a prompt such as “a photo of a suitcase” is a configuration change, and the storage schema already supports extra labels. What would still be missing: linking a bag to the person carrying it, a notion of physical size (“large” is only pixel size, which depends on distance), and cross-camera identity for bags (there is no Re-ID model for objects). Small objects are also harder for OWL-ViT B/32 at 768 px. Do not claim this works.
What is the difference between track_id and global_id?
track_id is ByteTrack's local number on one camera (and one connection); it restarts after a reconnect. global_id comes from FastReID matching against the identity gallery and means “the same individual across cameras and over time”. They are separate columns and never substituted for each other.
Can the LLM run SQL or delete data? What about prompt injection?
No. The LLM only returns JSON that must match a strict schema. The planner is deterministic code with five allow-listed operations; all SQL is fixed text with bound parameters; Track B's database connection is read-only. Tests scan the query code for execution primitives and run real injection prompts against the real model to confirm nothing changes. The remaining risk is a misread question (e.g. a wrong camera), which is visible in the provenance.
How do you prevent hallucinated answers?
Answer text is produced from templates filled with database rows; every camera, id and time is checked to exist; “no result” is phrased as “nothing stored”, not “nothing happened”; failures produce SYSTEM_ERROR, not an empty answer. LLM rewording is off by default and, when on, is rejected if any number or id changes.
What if two people look alike, or one person is split into two identities?
Matching requires similarity ≥ 0.70 and a 0.05 lead over the next identity; anything unclear stays ambiguous with candidates listed. So splits (duplicate ids) are more likely than wrong merges, on purpose. If a wrong merge happens anyway, the path reconstructor flags impossible transitions (too fast / two places at once) and warns that the id may cover two objects.
What if SQLite and ChromaDB disagree after a crash?
Write order guarantees only orphans can exist (a vector without a row), never a row pointing to a missing vector or video. recover() runs on start; reconcile() lists orphans, missing/altered clips and identities without vectors, and fix=True cleans them without deleting referenced evidence.
How do you know a clip is genuine and complete?
It is only referenced after ffmpeg finished cleanly and ffprobe confirmed codec, size and frame count. Its size and SHA-256 are stored; every answer and download checks the size, and a deep reconcile re-computes the SHA-256.
Why ChromaDB and not FAISS or pgvector?
The specification requires ChromaDB. Practically, it gives persistence, ids, metadata filters and an HNSW index in an embedded library with no server, which fits one local machine. FAISS is only an index library (no persistence or metadata); pgvector needs a PostgreSQL server.
Why Qwen3-8B and not Llama 3?
It was the 8B model available on the machine; the deviation was approved and documented. It runs locally (no cloud), at temperature 0 with schema-constrained JSON. Switching is one config line plus re-running the LLM tests.
How fast is it?
Measured on an RTX 5050 laptop: detection ≈ 10 ms, Re-ID ≈ 13 ms, storage write ≈ 3 ms per frame; capture → stored in 29 ms (median) for one camera; about 29 sampled frames per second total (≈ 8 simulated cameras) with one pipeline thread. In the load test, the median question took 1.2 s with the local LLM and 1.9 s with the LLM on the Ray peer (earlier single LLM calls were measured at 2–8 s). These are single runs on one laptop, not a benchmark suite.
Why are clips 5 fps and why do they play fast?
Only sampled frames (2–5 fps) are analysed and recorded, which keeps CPU, RAM and disk manageable. They are encoded at a fixed 5 fps, so slower-sampled segments play faster than real time; frame_ts keeps the true time of each frame, and the evidence player uses it.
What about privacy?
Privacy masks can blur or black out regions before analysis and storage, and the store refuses unmasked frames when masks are configured. Everything runs locally; the web console is loopback-only with a token. Missing: encryption at rest, per-person deletion, automatic retention.
Is it production-ready?
No, and the project's own final audit says so: no real cameras or long soak test yet, Re-ID thresholds and camera topology need site calibration, no TLS or per-user accounts. Architecture conformance passed, and 228 tests pass (1 skipped: RTMP).

10 · Honest limitations (from the project's own audit)

  • Tested on synthetic streams and one non-CCTV video; no real cameras, no multi-hour soak test; RTMP is wired but not verified.
  • Only 6 object labels are detected and searchable (person, car, truck, bus, motorcycle, bicycle). Bags, suitcases and other carried objects are not detected or stored; there is no person↔object association.
  • Re-ID thresholds are uncalibrated defaults; vehicle Re-ID is unvalidated; attribute search (“red jacket”) is approximate.
  • Camera topology is a placeholder, so cross-camera transitions are reported as unverified.
  • Track A is a single pipeline thread (~29 sampled fps); more cameras need multiple processes (not built). ChromaDB access from two processes while writing is not verified.
  • Timestamps are wall-clock at capture, not stream PTS.
  • A camera named in a path question acts as a filter (“where did he go after the lobby?” shows only lobby visits). See the demo trap in section 8.
  • Security is fine for one local user only: no TLS, single token, no encryption at rest, FastReID weights loaded with pickle and not checksum-verified.
  • Storage growth over days is unmeasured; only manual clip retention exists.
